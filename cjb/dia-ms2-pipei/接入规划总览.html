§3 PFMB 应该是什么层次

结论：MS2 预计算注释 sidecar —— 与 spectrum_memory 并列，不替代、不入库
PFMB 不是新的导入格式，也不替换现有 mzML 链路。它是已导入 DIA-NN 数据集的可选增强层， 按 dataset.capabilities.has_ms2_pfmb 开关控制。文件保持在磁盘原位，API 按需读取， 类比 mzML 的 spectrum_memory 方式（只是不放进内存，直接 O(1) 磁盘随机访问）。
维度 现有层（mzML spectrum_memory） 新增层（PFMB sidecar）
文件类型*.mzML / Bruker *.dresults.pfmb + index.json
路径存储位置runs.file_path（DB）datasets.extra_metadata.ms2_annotation（JSONB）
加载方式进程内 LRU 缓存（spectrum_memory）磁盘 O(1) 随机读（PfmbReader 持句柄）
匹配计算打开时实时算（theoretical_fragments）已算好，直接反序列化
离子系列b/y（charge 1,2）b/y/c/z·（全系列）
时间粒度apex RT 或 XIC 选点（1 个 scan）每个 RT slot 独立一条（6~10 个）
数据规模MS2 scan 数 ≈ 10 万级83.4 万条预计算记录
开关has_ms2 / spectra_sourcehas_ms2_pfmb（新增 capability）
是否必须是（DIA-NN 数据集核心功能）否（可选，sidecar 不存在时降级）

§4 核心技术问题：match_id ↔ source_row 映射

这是接入的最关键前置问题。必须先确认 DIA-NN parquet 的过滤行顺序和 pos.pkl 行顺序是否一致，才能确定映射策略。

方案 A：导入时写入（顺序一致时推荐）

如果 parquet 过滤后的行顺序与 pos.pkl 行号一一对应， 在 _collect_entities_and_matches 里按行计数写入 extra_metadata.source_row。 

# universal_diann_adapter.py
for idx, row in enumerate(rows):
    matches.append({
        ...
        "extra_metadata": {
            ...match_extra_metadata(row),
            "source_row": idx,  # 新增
        }
    })
查询快 O(1) 无需运行时计算 需确认行序一致

方案 B：运行时按 peptide+charge 查（顺序不确定时兜底）

用 match 的 sequence、precursor_charge 到 index.json 里查对应 slots， index.json 启动时一次性建内存索引。 

# index_reader.py
# 启动时建 (peptide, charge) → [slot_items] 索引
_idx: dict[tuple[str,int], list[SlotItem]]

def get_slots(peptide: str, charge: int):
    return _idx.get((peptide, charge), [])
无需改导入 index.json 200MB 内存索引 首次加载慢

capabilities 和 extra_metadata 写法（universal_diann_adapter.py）

def _detect_pfmb_sidecar(root: Path) -> dict | None:
    # 在 root 下或 root 父目录的 dia-ms2-pipei 子目录里查找
    candidates = [
        root / "data" / "results.pfmb",                         # sidecar 在同级
        root.parent / "dia-ms2-pipei" / "Hela_DIA_v2_for_frontend"
              / "data" / "results.pfmb",                         # viewer 目录约定
    ]
    for pfmb in candidates:
        idx = pfmb.parent / "index.json"
        if pfmb.exists() and idx.exists():
            return {"pfmb_path": str(pfmb), "index_path": str(idx)}
    return None

# _create_dataset 里
sidecar = _detect_pfmb_sidecar(root)
caps["has_ms2_pfmb"] = sidecar is not None
if sidecar:
    extra["ms2_annotation"] = sidecar

§6 建议实施顺序

Step 1 — 确认映射关系（先做，不写代码）
对比 pos.pkl 行数（应 =110024）和 parquet 过滤后行数是否一致，确认 source_row 和 match_id 的对应规律。决定用方案 A（导入写死）还是方案 B（运行时查）。 这是整个接入的前置决策。
Step 2 — 新建 back/app/pfmb/ 读模块
把 dia-ms2-pipei/pfmb_io.py 的依赖（pfm 包）安装到后端 venv， 在 back/app/pfmb/reader.py 包装 PfmbReader，管理文件句柄生命周期。 写一个 pytest 读一条样例验证可行。
Step 3 — 扩展 schema + 新增 API
改 BuMatchedIon.ion_type（加 c/z_dot），新增 DTO， 新建 ms2_annotations.py 路由，硬编码 PFMB 路径先跑通 API 响应。
Step 4 — 导入时探测 sidecar
改 _create_dataset 加 _detect_pfmb_sidecar()， 把路径写入 datasets.capabilities.has_ms2_pfmb 和 extra_metadata.ms2_annotation。重新导入数据集验证。
Step 5 — 前端接入
BuMatchDetailPage 检测 capabilities.has_ms2_pfmb， 有则加载 slots 列表，渲染 RT slot 选择器，选中后拉 PFMB 注释替换 / 并列展示碎片表。 BuFragmentTable 支持 c/z· 标签样式。
Step 6（可选）— pos.pkl 热力图
读 frag.chrom（12行×N列矩阵），新增 /frag-chrom endpoint， 前端渲染碎片矩阵热力图。这是独立模块，可以最后做。

最小可验收目标（Steps 1-5 完成后）

  • Match 详情页出现「PFMB 注释」区块（当 has_ms2_pfmb=true）
  • 可选择不同 RT slot 查看对应预计算匹配
  • 碎片表显示 b/y/c/z· 四种离子系列
  • has_ms2_pfmb=false 时页面不变，零影响现有功能
  • PFMB 读取 O(1)，响应 <200ms
  • 现有 mzML MS2 链路完全保留不动
