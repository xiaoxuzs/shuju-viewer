BU XIC 的 M+1 / M+2 全新实现规划

本规划基于当前 front 与 back 构成的网站实现：先完整梳理数据集入口、BU 页面、API 与现有单通道 M 曲线，再提出一套低耦合、可回退、可测试的 M+1 / M+2 同位素 XIC 实现方法。

只做规划，不改业务代码 范围：Bottom-Up match detail XIC 文件：docs/M+1-M+2实现规划.html 待确认后再实施

一句话方案

以现有 precursor_mz 作为 M，按 1.0033548378 / charge 计算 M+1 与 M+2 的目标 m/z，在 xic_service 的一次 MS1 遍历中同时提取三条 XIC 曲线。

API 保留旧字段 intensity，新增结构化 traces[]；前端优先渲染 traces，旧响应仍能显示单条 M 曲线。

网站理解 现有 M 质谱定义 新方法 API 契约 前端展示 文件清单 测试验收 待确认

1. 对当前网站内容的理解

全站入口

/datasets 是统一入口，展示 Top-Down 与 Bottom-Up 数据集卡片，支持本地文件夹导入、导入进度轮询、删除数据集。点击数据集后由 DatasetModeGate 按 analysis_mode 分流。

Top-Down 分支

Top-Down 使用 /datasets/:slug/:cutoff/proteins|proteoforms|prsms 路由，继续走已有 TD 页面与谱图组件。本次规划不改 TD 路由、TD API、PrSM 组件。

Bottom-Up 页面内容

页面 路径 当前内容 与 M+1/M+2 的关系
BU Layout /datasets/:slug 下的 BU 分支 页面标题、Bottom-Up / software / status 标记、Overview / Proteins / Peptides / Matches 标签页。 保留不变；M+1/M+2 不是新主导航。
Overview /datasets/:slug 摘要卡、QC、Run TIC/BPC 色谱、RT-m/z 鉴定热图、Bruker DIA windows、Run 列表。 不在整体页预拉 match 级同位素 XIC，避免大 I/O。
Proteins /proteins 与 /proteins/:id 蛋白列表、decoy 切换、蛋白详情、Sequence coverage、关联肽段表。 不请求谱图 API，不加入 M+1/M+2。
Peptides /peptides 与 /peptides/:id 肽段列表、q_max 过滤、肽段详情、关联 match 摘要。 可从 match 摘要跳详情；不在肽段页批量提 XIC。
Matches /matches 与 /matches/:id 鉴定列表含 sequence、run、protein group、m/z、z、RT、Q.Value、intensity；详情页含 match 摘要、XIC、MS1、MS2+b/y、Bruker mobility slice。 唯一需要改造的页面是 match detail 里的 XIC 卡片和放大弹窗。

后端模块边界

api/v1/bu/*

路由层只做 dataset/match guard、参数接收、调用 service、返回 DTO。

back/app/bu/services/*

运行时计算层：overview、lists、chromatogram、scan_resolver、spectrum_facade、theoretical_fragments、xic_service。

spectrum_memory

mzML 数据集预载与 run spectra 读取。BU 当前复用它，不在本次规划中修改它。

2. 现有“只有 M”的实现位置

当前 BU match detail 页打开后，前端并行请求 fetchBuMatchXic()、fetchBuMatchMs1()、fetchBuMatchMs2()。其中 XIC 走：

1. 前端BuMatchDetailPage 请求 /matches/{id}/xic?ppm=10
2. 路由matches.py 调用 xic_service.get_match_xic
3. 数据require_bu_match 提供 precursor_mz、charge、RT、run_id
4. 谱图get_run_spectra 从 spectrum_memory 取得 mzML run spectra
5. 计算遍历 MS1 scan，在 precursor_mz ± ppm 内取最大强度
6. 展示BuXicChart 把 rt[] 与 intensity[] 画成单条曲线
结论：现有 M 不是一个单独命名的“M 模块”，而是 BuXicOut.precursor_mz + BuXicOut.intensity 的单目标提取结果。M+1/M+2 的自然改造点是 xic_service 的目标 m/z 生成与多曲线输出，而不是导入流程、DB 大表或列表页。

3. M / M+1 / M+2 的质谱定义

标签 含义 用于 XIC 的目标 m/z 展示预期
M 单同位素前体峰，即当前 DIA-NN 鉴定给出的 precursor m/z。 precursor_mz 保留蓝色主曲线，是旧字段 intensity 对应曲线。
M+1 比 M 重约 1 个中子质量差的同位素峰，常见来源是一个 13C 替代 12C。 precursor_mz + 1.0033548378 / z 与 M 在 RT 上应基本共洗脱，强度通常低于 M。
M+2 比 M 重约 2 个中子质量差的同位素峰，常见来源是两个 +1 同位素替代或其他天然同位素组合。 precursor_mz + 2 * 1.0033548378 / z 与 M/M+1 共用 RT 轴，通常更弱，可帮助判断同位素包络一致性。
关键取舍：本次建议不先做完整同位素丰度建模，也不解析修饰质量。原因是 XIC 提取首先需要准确的目标 m/z；用已鉴定的 precursor_mz 做 M 锚点，再按 charge 计算同位素间隔，能避开 modified sequence 解析复杂度，并与当前数据库字段完全对齐。

4.2 XIC 服务一次遍历提取多目标

改造 xic_service.get_match_xic：先生成目标列表，再沿用现有 RT 窗口和 mzML MS1 遍历。每个 MS1 scan 内同时计算三个窗口的最大峰强度，最终返回共享 rt[] 与多条 trace。 

targets = build_precursor_isotope_targets(precursor_mz, precursor_charge)
series = {target.label: [] for target in targets}

for spec in ms1_scans_in_rt_window:
    spec_rt = rt_seconds / 60
    rt.append(spec_rt)
    best_by_target = extract_best_intensities(mz_values, intensity_values, targets, ppm)
    for target in targets:
        series[target.label].append(best_by_target[target.label])

4.3 扫描峰列表的性能策略

策略 说明 规划结论
简单三目标循环 每个 scan 内遍历峰数组，并同时更新 M/M+1/M+2 的 best intensity。 实现最直观，RT 窗口仅 apex 附近，足够作为第一版。
有序 m/z 二分 若 mz[] 单调递增，可对每个 target 用二分定位窗口，仅扫描局部峰。 可作为同一 helper 的优化，不改变 API。
调用三次旧 XIC 对 M/M+1/M+2 分别遍历一次 run spectra。 不采用；I/O 与循环成本被放大，且 RT 点排序更难统一。
模块边界：M+1/M+2 只增加 BU runtime service、BU DTO、BU 前端图表能力和测试；不改变导入链路、不新增 DB 列、不修改 Top-Down、不把算法塞进路由函数。

5. API 契约设计

endpoint 保持不变：GET /api/v1/datasets/{slug}/matches/{match_id}/xic?ppm=10。为了兼容旧前端，原字段保留；为了避免以后再加 M+3、M+4 时继续平铺字段，新增结构化 traces。

字段 状态 说明
rt 保留 三条曲线共享同一 RT 数组。
intensity 保留 永远等于 traces[0].intensity，即 M 曲线。
precursor_mz 保留 永远等于 M 的 target m/z。
precursor_charge 新增 前端标题和异常判断需要；来自 identification_matches.precursor_charge。
traces 新增 结构化承载 M/M+1/M+2，未来扩展不需要再改字段名。

8. 测试与验收标准

后端测试

  1. build_precursor_isotope_targets(477.305145, 2) 返回 477.305145、477.806822、478.308500 附近的三个 target。
  2. mock MS1 spectra 同时包含 M/M+1/M+2 峰时，get_match_xic 返回三条等长 trace。
  3. out.intensity == out.traces[0].intensity，保证旧字段兼容。
  4. charge 缺失或非法时不报错，只返回 M trace。
  5. Bruker .d match 仍按当前行为返回 unsupported_raw_format，不偷偷伪造 XIC。

前端验收

  1. match detail 的 XIC 卡片和放大 modal 都显示 M/M+1/M+2 三条曲线。
  2. 旧式响应缺少 traces 时，页面仍显示单条 M 曲线。
  3. TIC/BPC、RT-mz、MS1、MS2+b/y、protein coverage 页面不发生布局和请求回归。
  4. tooltip 能在同一个 RT 点显示多条曲线的强度。

9. 需要你确认的默认假设

  1. 本次只做 mzML 的 BU match detail XIC；Bruker .d 的 match-level XIC 仍保持当前不支持状态。
  2. M+1/M+2 的 m/z 使用 precursor_mz + n * 1.0033548378 / charge，不做完整 isotope abundance 模型。
  3. API 路径不变，默认总是返回 M/M+1/M+2；旧字段 intensity 继续代表 M。
  4. 前端第一版直接叠加三线，暂不新增图例点击开关到正式组件；若你需要，也可以把上方模拟图里的显示开关纳入实现。
确认后实施顺序：先做后端 target 模块与 XIC DTO/服务测试，再做前端类型与多曲线渲染，最后跑后端 pytest 与前端 TypeScript/build 检查。
