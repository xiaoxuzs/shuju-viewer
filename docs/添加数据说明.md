# Universal Viewer：添加数据说明

本文说明如何把一套新的 TopPIC / TopFD 结果包导入到 `Universal_Viewer` 新数据库。

当前方案采用 **Universal Viewer 7 表结构**，并使用快速导入模式：

- 谱图峰列表不写入 PostgreSQL。
- PrSM 详情不在导入阶段全量解析。
- 数据库只登记数据集、文件位置、蛋白、proteoform、匹配摘要和详情路径。
- 用户打开详情页时，后端再按需读取 `prsm*.js` 和 `spectrum*.js`。

---

## 1. 前置条件

1. PostgreSQL 已安装并运行。
2. 已创建数据库：

   ```text
   Universal_Viewer
   ```

3. `Universal_Viewer` 中已创建 7 张核心表：

   ```text
   datasets
   runs
   proteins
   peptides
   proteoforms
   identification_matches
   protein_relation_mapping
   ```

4. 后端依赖已安装：

   ```powershell
   cd back
   uv sync
   ```

5. `back/.env` 已指向新数据库：

   ```text
   DATABASE_URL=postgresql+psycopg://postgres:1wsx3qaz@localhost:5432/Universal_Viewer
   DATA_ROOT=../shuju
   API_CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
   LOG_LEVEL=INFO
   SPECTRUM_CACHE_SIZE=256
   ```

修改 `.env` 后需要重启后端服务。

---

## 2. 数据目录要求

TopPIC / TopFD HTML 输出目录应保持原始结构。

示例：

```text
<root>/
  topfd/
    ms1_json/spectrum*.js
    ms2_json/spectrum*.js
  toppic_prsm_cutoff/data_js/
    proteins.js
    prsms/prsm*.js
  toppic_proteoform_cutoff/data_js/
    proteins.js
    prsms/prsm*.js
```

当前已导入的数据集路径：

```text
E:/viewer/shuju/MZ20160222DS_histone48_html
```

说明：

- `proteins.js`：导入阶段最关键的文件，包含 protein、compatible proteoform 和 PrSM 摘要。
- `prsms/prsm*.js`：PrSM 详情文件，fast 模式不逐个解析，只登记路径，详情页按需读取。
- `topfd/ms1_json`、`topfd/ms2_json`：谱图文件目录，谱图峰列表不入库，前端画谱时由后端按需读取。

## 3. 导入命令

在 `viewer/back/` 目录执行：

```powershell
uv run python -m app.ingest.universal_toppic_adapter `
  --root "E:/viewer/shuju/MZ20160222DS_histone48_html" `
  --database-url "postgresql+psycopg://postgres:1wsx3qaz@localhost:5432/Universal_Viewer" `
  --slug mz20160222ds_histone48 `
  --name MZ20160222DS_histone48_html `
  --mode fast `
  --replace
```

参数说明：

- `--root`：TopPIC / TopFD HTML 输出目录的绝对路径。
- `--database-url`：目标数据库连接串。
- `--slug`：数据集唯一标识，用于前端 URL 和后端查询。
- `--name`：数据集展示名称。
- `--mode fast`：快速导入模式，只读 `proteins.js`，不逐个打开所有 `prsm*.js`。
- `--mode full`：完整摘要模式，会逐个解析 `prsm*.js`，导入更慢。
- `--replace`：如果数据库中已有相同 `slug` 的数据集，先删除旧数据再重新导入。

推荐默认使用：

```text
--mode fast
```

## 4. fast 模式导入方法

fast 模式的核心思路是：

```text
读取 proteins.js
  -> 写 datasets
  -> 写 runs
  -> 写 proteins
  -> 写 proteoforms
  -> 写 protein_relation_mapping
  -> 从 proteins.js 中的 prsm 摘要写 identification_matches
  -> 只登记 prsm*.js 的 detail_path
```

fast 模式不会做：

- 不读取 `topfd/ms1_json/spectrum*.js` 峰列表。
- 不读取 `topfd/ms2_json/spectrum*.js` 峰列表。
- 不逐个打开全部 `prsm*.js`。
- 不把完整 `ms_header`、`ms_peaks`、`annotated_protein` 提前写入数据库。

详情页需要时才会做：

```text
根据 identification_matches.detail_path
读取对应 prsm*.js
解析 ms_header / ms_peaks / annotated_protein
返回给前端
```

## 5. 导入进库的内容

### 5.1 datasets

写入 1 条数据集记录。

主要字段：

- `dataset_name`：数据集展示名称。
- `slug`：数据集唯一标识。
- `analysis_mode`：固定为 `TOP_DOWN`。
- `source_software`：固定为 `TopPIC_TopFD`。
- `source_root`：数据集根目录。
- `status`：导入完成后为 `READY`。
- `capabilities`：声明有 MS1、MS2、PrSM、proteoform、谱图文件，且谱图不入库。

### 5.2 runs

写入 1 条运行记录。

主要字段：

- `dataset_id`：关联 `datasets`。
- `file_path`：数据集根目录。
- `file_name`：目录名。
- `analysis_mode`：固定为 `TOP_DOWN`。
- `software`：固定为 `TopPIC_TopFD`。
- `status`：导入完成后为 `READY`。

### 5.3 proteins

从 `toppic_*_cutoff/data_js/proteins.js` 写入。

主要字段：

- `accession`：使用 TopPIC 的 `sequence_name`。
- `description`：使用 `sequence_description`。
- `is_decoy`：根据名称或描述中是否包含 decoy / reverse 判断。
- `extra_metadata`：保存 TopPIC 来源字段。

`extra_metadata` 包括：

```json
{
  "source_sequence_id": 0,
  "source_sequence_name": "sp|P10853|H2B1F_MOUSE",
  "compatible_proteoform_number": 107,
  "prsm_number": 793,
  "best_prsm_id": 2509,
  "best_prsm_e_value": 2.21e-80
}
```

### 5.4 peptides

当前 TopPIC / TopFD 数据是 Top-down 数据，不写入 `peptides`。

因此当前结果中：

```text
peptides = 0
```

以后接入 Bottom-up 数据时，才会写入 `peptides`，并在 `identification_matches.entity_type` 中使用 `PEPTIDE`。

### 5.5 proteoforms

从 `proteins.js` 中的 `compatible_proteoform` 写入。

主要字段：

- `modifications`：fast 模式默认写 `[]`。
- `start_res`：当前可空。
- `end_res`：当前可空。
- `theoretical_mass`：如摘要中能得到则写入，否则可空。
- `extra_metadata`：保存 TopPIC proteoform 来源字段。

`extra_metadata` 包括：

```json
{
  "source_sequence_id": 0,
  "source_proteoform_id": 0,
  "sequence_name": "sp|P10853|H2B1F_MOUSE",
  "source_cutoff": "prsm",
  "prsm_number": 143,
  "best_prsm_id": 2509,
  "best_prsm_e_value": 2.21e-80
}
```

### 5.6 protein_relation_mapping

写入 protein -> proteoform 归属关系。

主要字段：

- `protein_id`：关联 `proteins.protein_id`。
- `entity_type`：固定为 `PROTEOFORM`。
- `entity_id`：对应 `proteoforms.proteoform_id`。
- `is_unique`：当前默认 `false`。
- `extra_metadata`：保存来源 `sequence_id`、`proteoform_id` 和 cutoff。

### 5.7 identification_matches

从 `proteins.js` 中的 PrSM 摘要写入。

fast 模式只写摘要字段和详情路径。

主要字段：

- `dataset_id`：所属数据集。
- `run_id`：所属运行。
- `scan_number`：fast 模式暂写 `-1`，详情页按需读取 `prsm*.js` 后可得到真实 scan。
- `ms_level`：固定为 `2`。
- `entity_type`：固定为 `PROTEOFORM`。
- `entity_id`：对应 `proteoforms.proteoform_id`。
- `e_value`：TopPIC 摘要中的 `e_value`。
- `q_value`：TopPIC 摘要中的 `fdr`。
- `search_engine`：固定为 `TopPIC`。
- `detail_path`：对应 `prsms/prsm<ID>.js` 的路径。
- `extra_metadata`：保存 TopPIC PrSM 摘要字段。

`extra_metadata` 包括：

```json
{
  "source_cutoff": "prsm",
  "source_prsm_id": 2509,
  "p_value": 2.21e-80,
  "matched_fragment_number": 88,
  "matched_peak_number": 130,
  "ms1_ids": null,
  "ms2_ids": null,
  "ms1_scans": null,
  "ms2_scans": null,
  "source_sequence_id": 0,
  "source_proteoform_id": 0,
  "import_mode": "fast"
}
```

## 7. 如何验证导入成功

### 7.1 在数据库中查看计数

可以在 PostgreSQL 查询工具执行：

```sql
SELECT count(*) FROM datasets;
SELECT count(*) FROM runs;
SELECT count(*) FROM proteins;
SELECT count(*) FROM peptides;
SELECT count(*) FROM proteoforms;
SELECT count(*) FROM identification_matches;
SELECT count(*) FROM protein_relation_mapping;
```

查看 match 来源：

```sql
SELECT
  jsonb_extract_path_text(extra_metadata, 'source_cutoff') AS source_cutoff,
  count(*)
FROM identification_matches
GROUP BY source_cutoff
ORDER BY source_cutoff;
```

查看导入模式：

```sql
SELECT
  jsonb_extract_path_text(extra_metadata, 'import_mode') AS import_mode,
  count(*)
FROM identification_matches
GROUP BY import_mode;
```

### 7.2 在前端验证

1. 重启后端。
2. 重启或刷新前端。
3. 打开数据集列表。
4. 确认能看到 `MZ20160222DS_histone48_html`。
5. 进入 Protein / Proteoform / PrSM 列表。
6. 打开 PrSM 详情，确认序列、匹配峰和谱图能正常显示。

## 8. 常见问题

### Q：为什么数据库里没有谱图峰列表？

因为当前设计明确规定谱图不入库。

数据库只保存路径和索引，谱图文件仍然在：

```text
topfd/ms1_json/
topfd/ms2_json/
```

后端在前端请求谱图时按需读取。

### Q：为什么 fast 模式里 `scan_number = -1`？

fast 模式不逐个打开 `prsm*.js`，而 `scan_number` 在 PrSM 详情文件的 `ms_header` 中。

为了 30 秒内快速导入，fast 模式先登记 `detail_path`，详情页打开时再读取真实 scan、ms ids 和前体信息。

### Q：如果想把 scan 和 precursor 信息提前写进数据库怎么办？

使用 full 模式：

```powershell
uv run python -m app.ingest.universal_toppic_adapter `
  --root "E:/viewer/shuju/MZ20160222DS_histone48_html" `
  --database-url "postgresql+psycopg://postgres:1wsx3qaz@localhost:5432/Universal_Viewer" `
  --slug mz20160222ds_histone48 `
  --name MZ20160222DS_histone48_html `
  --mode full `
  --replace
```

full 模式会逐个解析 `prsm*.js`，导入时间明显更长。

### Q：导入后前端还是读取旧数据怎么办？

确认 `back/.env` 指向：

```text
postgresql+psycopg://postgres:1wsx3qaz@localhost:5432/Universal_Viewer
```

然后重启后端服务。旧后端进程不会自动读取新的 `.env`。
