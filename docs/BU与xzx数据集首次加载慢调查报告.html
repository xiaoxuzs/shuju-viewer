BU 与 xzx 数据集首次加载慢调查报告

调查日期：2026-06-09；范围：只读检查现有前后端、日志、数据库执行计划及数据文件，不修改业务代码。

结论

两个数据集首次点击都慢的共同根因，是“数据集详情接口”在返回少量元数据之前，同步完整解析该数据集的全部 mzML，并把全部谱峰转换为 Python 字典和列表常驻内存。

这个加载动作位于所有数据集入口的必经路径，而不是等用户真正打开谱图时再执行。因此页面会一直等待原始谱文件加载完成。

BU 还有一个额外瓶颈：概览页会立即并发计算 overview、TIC/BPC 和 RT–m/z 热图。热图接口读取 110,026 行到 Python 后逐点分箱；TIC/BPC 则遍历常驻内存中的全部 MS1 峰。它们继续延长首屏图表完成时间。

共同加载链路

点击数据集卡片
→ 前端 DatasetModeGate 请求 GET /api/v1/datasets/{slug}
→ 后端 get_dataset_detail()
→ _ensure_dataset_spectra_resident()
→ ensure_mzml_dataset_resident()
→ DatasetMzmlBundle.load()
→ load_mzml_path_to_scan_map()
→ 完整遍历 mzML，并将每张谱的 m/z、intensity 数组执行 tolist()
→ 全部完成后，详情接口才返回

关键代码证据

  • front/src/features/bu/routes/DatasetModeGate.tsx：进入任何数据集先调用 fetchDataset(slug)。
  • back/app/api/v1/datasets.py:181-202：get_dataset_detail 在构造详情响应前调用 _ensure_dataset_spectra_resident。
  • back/app/services/spectrum_memory_wiring.py：根据数据库中的 run 映射出全部 mzML，然后调用全数据集常驻接口。
  • back/app/spectrum_memory/mzml_dataset_bundle.py:20-28：逐个文件调用完整加载函数。
  • back/app/spectrum_memory/mzml_spectrum_extract.py:68-76：每张谱的 NumPy 数组被转为 Python list。
  • back/app/spectrum_memory/mzml_spectrum_extract.py:80-101：完整读取文件并建立 scan_number → spectrum 映射，没有按需读取。

数据规模与实测

项目 xzx_PXD045330 BU PR1 DIA
谱图模式 mzml_memory mixed，其中 mzML run 会被整体加载
mzML 文件大小 31,408,514 B（约 29.95 MiB） 1,445,130,808 B（约 1.346 GiB）
项目同一解析函数实测 1.402 s；2,048 scans；估算对象 115,073,168 B 未在第二进程重复完整解析，避免额外占用约 5 GiB 以上内存
详情接口热缓存 约 19–22 ms 约 17–19 ms
预加载内存预留公式 磁盘大小 × 4，加每 run 64 KiB 约 5.38 GiB 预留

实测xzx 的磁盘文件只有约 30 MiB，但转成项目当前 Python 对象后约为 109.7 MiB，膨胀约 3.66 倍。

实测后端工作进程当前私有内存约 6.842 GiB，工作集约 0.605 GiB，说明大量已分配内存已被 Windows 换出或不在物理工作集。

推算BU 使用同一加载算法处理 1.346 GiB mzML。按代码自身的 4 倍预留公式，单次加载就需要约 5.38 GiB；按 xzx 的实测膨胀比例，量级同样接近 5 GiB。首次点击时的主要等待就是这次解析和对象构建。

未重启正在运行的后端，因此没有为了报告强制制造一次 BU 冷启动。BU 冷加载结论由确定的调用链、精确文件大小、代码预留公式和当前进程内存共同证明；报告没有虚构一个未测得的冷启动秒数。

BU 的额外耗时

BU 详情元数据返回后，BuOverviewPage 会继续发起三个主要请求。2026-06-09 的本机热态实测如下：

接口 第一次记录 随后热态记录 主要工作
/overview 881.6 ms 240.6–377.2 ms 多项 count 聚合，并按 run 统计 matches
/runs/39/chromatogram?type=tic 1,585.2 ms 723.8–764.5 ms 遍历该 run 全部常驻谱；对每张 MS1 的 intensity list 求和
/overview/rt-mz 16,405.6 ms 1,763.0–2,466.2 ms 取回 110,026 行，再在 Python 中创建对象、求范围并逐点分箱

数据库是否是主要原因

已排除为主因针对 RT–m/z 查询执行只读 EXPLAIN ANALYZE，数据库执行时间约 76.3 ms，返回 110,026 行。虽然执行计划选择了顺序扫描，但 SQL 本身远低于接口的 1.7–16.4 s。

差额主要发生在数据库结果传输、SQLAlchemy 行对象化、Python list 构建、两次数组提取、80×80 矩阵创建、110,026 点循环分箱、Pydantic 响应构造，以及高内存压力下的分页/缺页。

xzx 为什么也慢

xzx 首页本身没有 BU 的 overview、TIC 和热图请求。它的主要问题就是共享的数据集详情入口进行了不必要的整文件预加载。

  1. 用户只是打开数据集概览，尚未进入具体 PrSM 或谱图。
  2. 详情接口仍完整解析 31.4 MB mzML。
  3. 实测该解析单独需要 1.402 s，并创建约 115.1 MB 的谱图对象。
  4. 解析完成后，同一接口的热缓存请求只剩约 20 ms，冷热差异直接证明等待来自首次常驻过程。

放大因素

  • 内存表示膨胀：峰数组从紧凑 NumPy 数组转成 Python float list；每个数值和容器都有额外对象开销。
  • 同步阻塞：加载发生在普通详情 HTTP 请求内，接口不会先返回元数据，也没有后台加载阶段。
  • 粗略内存核算：全局池上限默认 6 GiB，但核算函数是估算值；Python 分配器、字典、字符串和解析临时对象不一定被完整计入。
  • 物理内存缺页：当前私有内存显著高于工作集，访问大对象时可能触发 Windows 页面换入，造成同一接口不同轮次耗时波动。
  • BU 首屏并发重活：详情接口结束后马上并发进行数据库聚合、全谱 TIC 和十万行热图处理，CPU、内存和数据库资源会互相竞争。

本次未发现的主因

  • 不是前端组件 BuPfmbAnnotationCard 导致数据集入口首次加载慢；该组件只在 match detail 页面使用。

调查限制

本次遵守“不修改代码”的要求，也没有停止或重启现有前后端。为避免与正在运行的约 6.84 GiB 后端进程叠加内存并导致系统失稳，没有在第二进程完整解析 BU 的 1.346 GiB mzML。所有标记为“推算”的数字均与实测数据分开陈述。

优化目标

优化不应只是把全量加载挪到后台，因为那仍会消耗约 5–7 GiB 内存。推荐目标是：数据集入口只读取元数据；谱图按需读取；概览图使用预聚合结果；任何单个页面都不再要求整份 mzML 转成 Python 对象常驻内存。

场景 建议验收目标 当前参考值
冷启动后打开 xzx/BU 数据集首页 详情接口 P95 ≤ 300 ms；不读取 mzML；后端内存无显著增长 xzx 解析约 1.402 s；BU 需要处理 1.346 GiB mzML
BU RT–m/z 热图 P95 ≤ 500 ms；后端最多返回 6,400 个聚合格子 热态约 1.7–2.5 s，首次记录 16.4 s

推荐实施顺序

第一阶段：先让数据集入口立即返回

P0从 GET /datasets/{slug} 中移除 _ensure_dataset_spectra_resident。该接口只负责返回数据集元数据、cutoff 和 BU run 摘要，不再触碰 mzML。

建议修改边界：

  • back/app/api/v1/datasets.py：详情路由不再负责谱图常驻。
  • back/app/services/spectrum_memory_wiring.py：保留为谱图访问层使用，不由元数据路由调用。
  • front/src/features/bu/routes/DatasetModeGate.tsx：无需为这一步重构；现有请求会自然变快。

效果：xzx 和 BU 数据集首页会首先恢复为轻量页面。即使后续谱图能力尚未完成优化，也不会再阻塞用户进入数据集。

注意：仅完成这一步会把等待从“打开数据集”移动到“第一次查看谱图”。因此它是必要的止血措施，但不是最终方案。

第二阶段：用按 scan 读取替代整数据集常驻

P0在 back/app/spectrum_memory/ 内建立窄接口，例如：

get_spectrum(dataset_id, run_id, scan_number)
get_spectra_in_rt_range(dataset_id, run_id, rt_start, rt_end)
get_run_summary(dataset_id, run_id)

接口背后的实现应使用 mzML 索引随机访问目标 scan，或在首次解析时生成轻量 sidecar 索引；不要再向 API 层暴露整份 run_to_spectra 字典。

  • 单张 MS1/MS2：只读取目标 scan；需要母子谱关系时读取少量相邻 scan。
  • Precursor XIC/Product XIC：按 RT 窗口读取相关 MS1/MS2，不遍历无关时间范围。
  • 缓存单位改为 scan 或小 RT 分块，并设置明确的字节上限和 LRU 淘汰。
  • 缓存内部保留 NumPy 数组；只在构造最终 JSON 响应时转换当前请求所需数组。

模块边界应保持低耦合：API 路由只调用谱图服务；谱图服务只依赖统一 reader 接口；mzML 索引、缓存和文件解析细节留在独立模块中。

第三阶段：把 BU RT–m/z 分箱放到数据库

P0（BU）当前实现把 110,026 个点全部取回 Python。应改为数据库完成分箱，只返回非空格子的 rt_bin、mz_bin、count。

推荐流程：

  1. 先查询当前过滤条件下的 min/max retention_time 与 min/max precursor_mz。
  2. 使用 PostgreSQL width_bucket 或等价表达式按 80×80 分组。
  3. 数据库执行 GROUP BY rt_bin, mz_bin，Python 只负责把最多 6,400 个格子放进响应矩阵。

涉及模块应限制在 back/app/bu/services/overview_service.py 及对应测试，不要把 SQL 拼装移到路由层。

不建议把“新增索引”当作第一解决方案。现有 SQL 的数据库执行时间实测约 76 ms，主要损耗发生在返回十万行之后。先减少返回行数，再根据新的执行计划决定是否增加复合或部分索引。

第四阶段：预生成 BU TIC/BPC 概览数据

P1（BU）TIC/BPC 是 run 级稳定派生数据，不应在每次请求中重新遍历全部 MS1 峰。

  • 优先在导入完成阶段生成 rt、tic、bpc 的下采样结果。
  • 结果可存为独立 sidecar 文件或专用小表；不要塞入万能 JSON 大字段。
  • 接口直接读取最多 8,000 个点，切换 TIC/BPC 时不再访问原始峰数组。
  • 旧数据集可提供独立的一次性回填命令，不要在普通 GET 请求中隐式回填。

建议新增独立的 BU 概览派生模块，由 ingest 编排调用其公开 API；不要把预计算逻辑写进 api/v1/bu/chromatogram.py。

第五阶段：优化 overview 聚合与前端加载节奏

P1（BU）/overview 中多个独立 count 子查询和 run 统计可继续优化，但优先级低于整包 mzML、热图和 TIC/BPC。

  • 检查是否能用一次条件聚合或小型汇总表返回稳定计数。
  • 稳定统计可在导入完成时写入专用 summary，而不是每次打开首页重算。
  • 前端继续让卡片独立显示 skeleton；某张图失败或较慢时，不阻塞数据集标题、导航和其他摘要。
  • 不要用单纯延长 React Query staleTime 掩盖后端问题；它只能改善同一浏览器会话的重复访问。

不推荐的做法

做法 为什么不推荐
应用启动时预热所有数据集 启动更慢、内存峰值更高，并且会加载用户可能根本不会访问的数据。
只把全量加载改成后台线程 页面入口会变快，但 5–7 GiB 内存和 CPU/I/O 成本仍存在，还会与正常请求争抢资源。
继续增大全局内存池 当前问题是对象表示和加载粒度不合理；增大上限只会推迟换页或 OOM。
只增加数据库索引 RT–m/z SQL 已经只需约 76 ms，无法解释接口的大部分耗时。
把所有优化塞进 datasets.py 或 overview_service.py 会破坏项目要求的低耦合、高模块化，使 mzML 读取、缓存、派生数据与路由再次混杂。

验证与交付建议

每个阶段都应先记录基线，再实施最小改动并复测。建议在 cs/ 中新增中文性能验收入口，同时在 back/tests/ 保留行为单元测试。

  1. 数据集入口测试：模拟 mzML reader，断言 GET /datasets/{slug} 不调用任何谱图加载函数。
  2. 按需读取测试：请求一个 scan，断言 reader 未遍历整份文件；重复请求验证小缓存命中。
  3. 热图一致性测试：用固定小数据比较数据库分箱与原 Python 算法的格子计数。
  4. TIC/BPC 一致性测试：比较预生成结果与原始算法，明确下采样误差边界。
  5. 性能脚本：分别记录冷启动详情、首次谱图、热图、TIC/BPC、进程私有内存和工作集。
  6. 回归测试：覆盖 xzx Top-Down PrSM 谱图、BU mzML match detail、BU Bruker run，避免只优化一种数据形态。

推荐交付顺序为：详情接口解耦 → RT–m/z 数据库分箱 → TIC/BPC 派生数据 → scan/RT 分块读取 → overview 次级优化。前两项改动范围较小、收益最直接；整套按需谱图读取应作为独立任务设计和验收。
